# 利用率感知的 max 模型能否选对 GEMM tile：离线检查（事后，未冻结）

目的：在为"最优映射器漏掉开销项"立项之前，先检查一个更忠实的 AccelForge 式模型
`max(计算, 访存)` 是否已经能选对 tile。只重新打分已归档的 PyTorchSim 运行
（`results/gemm_fidelity`、`results/gemm_cycle_model`，共 40 个（形状，预算）组），
没有新仿真，也没有事先冻结预测。脚本：`max_model_check.py`。

## 依据

一次运行的 TOGSim 统计（BERT-large QKV，tile (128,1024,8)）：两个脉动阵列各
active 65,770 周期，总周期 79,391；DMA active 10,240 周期，传输 10.5 MB。

- 按权重驻留阵列的 pass 数估算计算时间
  `迭代数 × tm × ceil(tn/128) × ceil(tk/128) / 2` = 65,536，与 active 周期相差 0.4%。
  tk 小时慢，是因为阵列只用了 tk/128 行，属于**空间利用率**问题，不是固定开销。
- DMA 在活跃时约 1,024 B/周期。此前周期模型拟合出的 390 B/周期是加法模型的产物，
  不是实际带宽。
- 总周期接近 max(计算, DMA) 加少量空转，说明访存和计算大部分是重叠的。

## 结果（带宽 1,024 B/周期）

| 模型 | 并列最优中最好的 tile：>1.1× 的组 | 并列最优中最差的 tile：中位 / 最大 |
| --- | ---: | --- |
| 纯流量（我们的 (C,Q)） | 11/40 | 3.81× / 13.39× |
| max，理想计算（不看 tk） | 11/40 | 3.81× / 13.39× |
| **max，计入阵列利用率** | **2/40** | 1.18× / 6.67× |
| 加法，计入利用率 | 12/40 | 1.16× / 2.06× |

## 结论

- 此前"流量最优的 tile 慢 1.8–6.9×"，主要是**我们自己的纯流量模型**造成的，因为它没有
  建模阵列的空间利用率。只要把 K 和 N 正确映射到 128×128 阵列，AccelForge 式的 max
  模型就能在 38/40 组里给出包含近最优 tile 的并列集合。
- 剩下的误差来自并列 tile 之间的选择，中位约 1.18×，属于填充排空和同步这类二阶项。
- 因此，"最优映射器（TCM/FFM）在 NPU 上系统性选错"这一主张**不成立**，不以此立项。

## 局限

- 候选 tile 是原协议按流量模型挑选的，不是预算内的全部 tile。
- 利用率公式和带宽只在一次运行的统计上核对过。
- 实际 AccelForge 规格的结果需要在服务器上运行才能确认；这里是解析式的等价近似，
  并非 AccelForge 本身的输出。
