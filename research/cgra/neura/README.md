# C2：在 Neura 上测多算子融合（2026-11-14）

结论：**C2 不成立，CGRA 方向停止。** 在 Neura 的执行模型下，融合最多带来约 1/N 的收益；II 由循环嵌套的深度决定，和数据复用结构无关。

## 设置

- Neura `21f0fa1`，对应 LLVM `6146a88f`，用 gcc 11 构建（`build_neura.sh`）。仓库自带的 `test/e2e/gemm` 测试通过。
- 流程和 Neura 的 gemm e2e 测试相同：先 `clang -O3 -fno-vectorize -fno-unroll-loops`，再 `mlir-translate --import-llvm`，最后跑 Neura 的整条 pass 流水线，用启发式映射到默认的 4×4 阵列（7 个可访存 tile，`ctrl_mem_items: 20`）。见 `run.sh`。
- kernel 全部是 int 类型，N=16，见 `kernels/`。
- 时间模型：整个函数被展平成一张谓词数据流图，**每个最内层迭代花一个 II**。周期数 ≈ II × 各循环嵌套的最内层迭代数之和。这个模型没有用 Zeonica 验证。

## 观察

1. **II 由循环深度决定**：两层嵌套的 RecMII 是 9，三层是 13，不管循环体里算的是什么都一样。这条递归来自展平后循环控制的谓词链，不是数据依赖。ResMII 只有 3–6。
2. **单次使用的消费者，融合收益上限约为 1/N**：消费者的工作量是 O(N²)，生产者是 O(N³)。即使理想融合，也最多省掉消费者那部分（N=16 时约 4.3%）。实测 ReLU 融合 1.045×，和上限一致。
3. **多保留一个累加器会让 II 从 14 涨到 16**，所以行求和融合反而变慢 9%。方向上符合角色超图的说法（多一个 c=2 的驻留就要多占资源），但量级只有几个百分点。
4. **工作量相当的消费者（GEMM → GEMM）必须复用中间结果**，因此需要缓冲区，DFG 也大到在 4×4 阵列上映射失败。这正是融合唯一可能有意义的情况，但工具做不到。
5. 把两个嵌套放进同一个函数（多 kernel 的做法）比分开映射差 19%：两张 DFG 共享阵列，II 是取较大者，而不是相加。

这和 `research/dnn_benchmarks/CROSS_OP_MAGNITUDE.md` 的教训一样：跨算子带来的收益上限很低，主导项在算子内部（这里是循环控制递归）。
